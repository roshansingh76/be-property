# Broker uploads and WhatsApp automation

Three interconnected problems are solved: brokers couldn't update property images or legal documents from web and mobile, and four new WhatsApp notification events needed to be wired into the route handlers. The backend fixes an authorization bug in the document upload route, adds a GET documents endpoint, and threads `enqueueWhatsApp` calls (all fire-and-forget) into images, documents, leads, and inquiries handlers. The web frontend adds two inline panel components to the seller dashboard. The Flutter app adds two bottom-sheet widgets and the platform-specific picker dependencies. All three builds pass clean.

Watch for: **confirmed** — Flutter's `PropertyService.fetchPropertyDocuments` casts the raw API response as `List` but the backend wraps documents in an object `{ "documents": [...] }`. This will throw a `TypeError` at runtime when a broker opens the Legal Documents sheet on mobile.

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The authorization bug fix in `workflows.ts` is correct: the old `||` → `&&` change means the check now requires *both* "not in ownerRoles" and "not the owner" before denying, so admins bypass ownership and broker-owners are allowed through. The companion mime-type gate (PDF/JPEG/PNG/WebP) is applied before the file is written to disk.

The four new `WhatsAppEventName` union members match exactly the four template keys added to `WHATSAPP_TEMPLATES`. Variable counts in each template's `variables` array match the `{{N}}` placeholder count in both English and Hindi bodies. All fire-and-forget calls are wrapped in `.catch(() => undefined)`, so a queue outage cannot break an upload or lead creation. The one `await enqueueWhatsApp` that is *not* fire-and-forget is the buyer ACK in `inquiries.ts` — that is pre-existing behavior and outside this diff's scope.

The frontend panels cover all required states (loading, error, empty, populated). `deletePropertyImage` strips the origin prefix before sending to the backend. `fetchPropertyDocuments` correctly unwraps `res.documents` from the `{ documents: [...] }` envelope.

The Flutter API client's `uploadDocument` and `deleteImage` follow the same multipart and DELETE-with-body patterns established by `uploadImages`. The relative-path stripping in `_relativePath()` in `ManageImagesSheet` mirrors the web client. **The documents layer has a blocking runtime bug**: `PropertyService.fetchPropertyDocuments` casts the raw GET response as `List`, but the backend returns `{ "documents": [...] }`. The web client correctly unwraps `.documents`; the Flutter side missed it.

### Flutter documents response shape mismatch

`GET /properties/:id/documents` returns `{ documents: PropertyDocument[] }` — this is consistent in both the backend (`return { documents }`) and the web frontend (`api.get<{ documents: PropertyDocument[] }>(...)`; then `res.documents`).

`ApiClient.fetchDocuments` does a plain `get()` which returns the parsed JSON body as `dynamic`. `PropertyService.fetchPropertyDocuments` then casts it directly as `List`:

```dart
final data = await ApiClient.fetchDocuments(propertyId) as List;
return data.map((e) => e as Map<String, dynamic>).toList();
```

The response body is `Map<String, dynamic>`, so `as List` throws immediately. `ManageDocumentsSheet` catches this in `_fetchDocs`, sets `_error`, and shows the error text — so it fails visibly, not silently. The fix is:

```dart
final data = await ApiClient.fetchDocuments(propertyId) as Map<String, dynamic>;
final list = data['documents'] as List;
return list.map((e) => e as Map<String, dynamic>).toList();
```

### WhatsApp template variable alignment

Confirmed counts:

| Template | Body placeholders | `variables` array length |
|---|---|---|
| `broker_images_uploaded` | 5 ({{1}}–{{5}}) | 5 ✓ |
| `broker_document_uploaded` | 4 | 4 ✓ |
| `new_property_inquiry_broker` | 4 | 4 ✓ |
| `new_lead_broker_notice` | 5 | 5 ✓ |

The `new_property_inquiry_broker` template in the plan described 5 variables (`broker_name, property_title, village, buyer_name, purpose`) but the implemented body only uses 4: `{{1}}` broker_name, `{{2}}` buyer_name, `{{3}}` purpose, `{{4}}` preferred_area. The `variables` array matches the implemented body (4 entries), so the `resolveTemplateBody` function will produce correct output.

### Image upload authorization scope

`POST /properties/:id/images` allows `isOwner || isAdmin`. Brokers who created properties own them (their `userId` is the `ownerId`), so they pass `isOwner`. Brokers uploading images for properties owned by a different user (e.g., a seller client) are correctly blocked unless they are admins. This is the intended design.

### Path traversal in uploads

Both the image handler (`properties.ts`) and the document handler (`workflows.ts`) sanitize filenames with `.replace(/[^a-zA-Z0-9._-]/g, "_").slice(0, 120)` before joining them under a property-scoped subdirectory. The image delete handler bounds-checks the resolved path against the uploads root before calling `unlink`. No traversal risk introduced.
