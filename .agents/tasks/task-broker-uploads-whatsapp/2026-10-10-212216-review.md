# Broker image/document uploads and WhatsApp automation

Brokers and sellers can now upload property images and legal documents from both the web dashboard and the Flutter mobile app, with WhatsApp notifications sent automatically to property owners and admin when a broker acts on their behalf. The backend fixes a pre-existing authorization bug in the document-upload route (`||` → `&&`), adds a `GET /properties/:id/documents` endpoint, extends four route handlers with `enqueueWhatsApp` calls, and adds four new template entries. The frontend adds `PropertyImagesPanel` and `PropertyDocumentsPanel` components wired into `SellerDashboard`. The Flutter app gains `ManageImagesSheet` and `ManageDocumentsSheet` bottom sheets plus two new `ApiClient` methods. All three builds pass clean (`tsc`, Next.js build, `flutter analyze`).

**Watch for:** (confirmed) The document-upload authorization fix allows any user in `ownerRoles` to upload documents to *any* property — not just their own — because `ownerRoles` includes `SELLER` and `BROKER`, and the `&&` condition only blocks someone who is *both* outside ownerRoles *and* not the owner. A plain `SELLER` who owns a different property passes the role check and can upload to listings they don't own. (confirmed) The `GET /properties/:id/documents` route has the same widened access issue. (confirmed) The frontend `property-documents-panel.tsx` imports `API_ORIGIN` but never uses it — harmless but dead import. (possible) Flutter `ManageImagesSheet` updates `_images` from the full `images` array returned by the backend but the backend's `POST images` returns `{ images: string[] }` with relative paths, while the sheet tries to display them via `fullImageUrl` — if `kApiOrigin` prefixing happens in `fullImageUrl` but the delete path stripping uses `kApiOrigin` too, this is consistent; worth confirming the `fullImageUrl` helper handles both prefixed and unprefixed URLs.

**Verdict**: CHANGES_REQUESTED

## High-level view

The authorization fix in `POST /properties/:id/documents` was meant to change `||` to `&&` to allow admins to upload to any property and owners to upload to their own. The intent is correct but the implementation is too wide: `ownerRoles` includes `SELLER` and `BROKER` in addition to `ADMIN`/`SUPER_ADMIN`, so any authenticated seller or broker clears the role check regardless of ownership. The `GET /properties/:id/documents` route shares the identical condition and has the same flaw.

The four new WhatsApp templates are all correctly structured and the `enqueueWhatsApp` calls in `properties.ts`, `workflows.ts`, `leads.ts`, and `inquiries.ts` are all wrapped in `.catch(() => undefined)`, satisfying the requirement that WhatsApp failures never break the main request flow.

The frontend panels cover loading, error, and empty states correctly. The images panel initialises with a deduped copy of `initialImages`, handles upload and delete inline, and propagates updates back to the dashboard via `onImagesUpdated`. The documents panel fetches on mount, shows a spinner during load, and re-fetches after upload. Both panels disable their inputs during in-flight requests.

The Flutter sheets follow the same pattern: loading overlay, error text, confirmation dialog before delete (images), snackbar on success (documents). The `ApiClient.deleteImage` method sends a proper `http.Request` with a JSON body, matching the backend's `DELETE /properties/:id/images` contract. `ApiClient.uploadDocument` is a multipart POST with a `documentType` field, matching the backend parser.

### Document upload and fetch authorization bug

The fixed condition in `POST /properties/:id/documents` is:

```ts
if (!ownerRoles.includes(request.authUser.role) && property.ownerId !== request.authUser.userId)
  return reply.code(403).send(...)
```

`ownerRoles` is `[SELLER, BROKER, AGENT, ADMIN, SUPER_ADMIN]`. Any authenticated `SELLER` passes `ownerRoles.includes(role)` → the whole condition short-circuits to `false` → no 403. That means a broker can upload documents to a property they did not create. The plan's intent was specifically to allow admins to bypass ownership while requiring non-admins to be the owner. The correct condition is:

```ts
const isAdmin = adminRoles.includes(request.authUser.role);
const isOwner = property.ownerId === request.authUser.userId;
if (!isAdmin && !isOwner) return reply.code(403).send(...)
```

`adminRoles` is `[ADMIN, SUPER_ADMIN]`. The `GET /properties/:id/documents` route has the same `ownerRoles` guard and needs the same fix. Both are confirmed blocking issues — the acceptance criterion "POST /properties/:id/documents returns 403 for users who neither own the property nor are admin" is not met under the current condition for a `SELLER` who doesn't own the property.

### Flutter image URL handling

`ManageImagesSheet` populates `fullImages` via `_images.map(fullImageUrl)` for display, and strips the origin with `_relativePath(imageUrl)` before calling delete. The backend `POST images` returns relative paths (`/uploads/...`); `ApiClient.uploadImages` returns the raw response without prefixing, so `_images` after an upload holds relative paths. `fullImageUrl` in `constants.dart` presumably prepends `kApiOrigin` — if so, display and delete are consistent. This is marked **possible** because `fullImageUrl`/`kApiOrigin` were not read, but the pattern matches the web client's handling.

### Dead import

`property-documents-panel.tsx` line 7 imports `API_ORIGIN` from `@/lib/api/client` but uses only `fetchPropertyDocuments`, `uploadPropertyDocument`, and `PropertyDocument`. `API_ORIGIN` is never referenced in the component body. The TypeScript build passes because it is a re-exported value (not a type-only import), but it's dead code.
