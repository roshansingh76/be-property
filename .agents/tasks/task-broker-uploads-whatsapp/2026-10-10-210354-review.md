# Broker image/document uploads + WhatsApp automation

Three previously blocked workflows now work: brokers can upload images and legal documents for their listings through both the web dashboard and the Flutter app, and four new WhatsApp events fire asynchronously when those actions occur (plus when new leads and general inquiries arrive).

**Watch for:**
- `imageUrl` path traversal in DELETE `/properties/:id/images` — the check `imageUrl.startsWith("/uploads/")` does not prevent `/../` segments in the stored URL (confirmed in `properties.ts`).
- `new_property_inquiry_broker` template declared in `types.ts` and `templates.ts` but never actually enqueued — `inquiries.ts` only sends `buyer_inquiry_ack` to the buyer; the admin/broker notification path described in FEAT-001 was not wired (confirmed by reading `inquiries.ts`).
- `enqueueWhatsApp` calls in `service.ts` fall back to `"buyer_inquiry_ack"` when `templateName` is omitted and no `message` is provided — all four new call sites omit `templateName`, so the stored `content` field on `WhatsAppMessage` records resolves to the wrong template body (confirmed in `service.ts` line 56).

**Verdict**: CHANGES_REQUESTED

## High-level view

The authorization fix in `workflows.ts` (`||` → `&&`) is correct and the mime-type whitelist on both document and image uploads is in place. The GET `/properties/:id/documents` endpoint uses the same guard condition as the POST, which is consistent.

The four new WhatsApp event names are added to `types.ts` and all four templates are defined in `templates.ts`. Variable counts in the template bodies match the `variables` arrays for all four entries. However, the `new_property_inquiry_broker` event type is unused — it has no call site in `inquiries.ts`, which only sends the buyer ACK.

All `enqueueWhatsApp` calls added to `properties.ts`, `workflows.ts`, and `leads.ts` are wrapped in `.catch(() => undefined)` and run outside the main reply path, so WhatsApp failures cannot break the upload or lead-creation response. The pattern is correct.

The `service.ts` `WhatsAppMessage.create` uses `templateName ?? "buyer_inquiry_ack"` as the fallback for the stored `content` field. Because the new call sites pass `eventName` but not `templateName`, the DB record always stores the `buyer_inquiry_ack` body instead of the actual template text. This is a data-quality bug in the audit log, not a delivery bug (the queue payload carries `eventName` and `variables` which the worker uses to build the real API call).

The web frontend panels handle loading, error, and empty states correctly. The Flutter sheets guard every async operation with `if (mounted)` checks and show loading overlays. Both `image_picker` and `file_picker` are pinned and present in `pubspec.yaml`.

The image delete path in `properties.ts` verifies that the URL exists in the property's `images` array before operating on it — this prevents deletion of arbitrary DB records. However, once the membership check passes, `path.join(process.cwd(), imageUrl)` is called without a `path.normalize` + prefix assertion, so a stored URL containing `/../` segments could escape the uploads directory on disk.

### Path traversal in image delete

The DELETE `/properties/:id/images` handler correctly verifies that `imageUrl` is a member of `property.images` before doing anything. This prevents deleting URLs that were never stored. However, the file-deletion code that follows trusts the stored URL string directly:

```ts
if (imageUrl.startsWith("/uploads/")) {
  const filePath = path.join(process.cwd(), imageUrl);
  await unlink(filePath).catch(() => { /* ignore */ });
}
```

`path.join` on Linux resolves `..` segments, so `/uploads/properties/x/../../../some/sensitive/file` passes the `startsWith` guard and maps to a path outside the uploads directory. Since URLs are written by the upload handler (which sanitizes filenames), this is not exploitable via normal upload→delete flow. But if a property record's `images` array were ever written directly (e.g., via the PATCH `/properties/:id` endpoint which accepts an `images: z.array(z.string().url())` field), the traversal path opens.

Fix pattern:
```ts
const resolved = path.resolve(process.cwd(), "uploads", imageUrl.slice(1));
const uploadsRoot = path.resolve(process.cwd(), "uploads");
if (resolved.startsWith(uploadsRoot + path.sep)) {
  await unlink(resolved).catch(() => {});
}
```

### `new_property_inquiry_broker` event has no call site

FEAT-001 step 8 (plan) and FEAT-001 step D describe sending `new_property_inquiry_broker` to `ADMIN_PHONE` when a new `BuyerInquiry` is created. Reading `inquiries.ts` in full: the only `enqueueWhatsApp` call sends `buyer_inquiry_ack` to `parsed.data.buyerPhone`. No admin/broker notification is sent. The template and type are defined but dead.

### Audit log records wrong template content

`service.ts` stores a `WhatsAppMessage` row immediately on enqueue. The `content` field is populated with:

```ts
content: message ?? resolveTemplateBody(templateName ?? "buyer_inquiry_ack", locale, variables)
```

For the four new events, `message` is undefined and `templateName` is not passed, so `resolveTemplateBody` renders the `buyer_inquiry_ack` template using the new event's variables — producing nonsensical text like "Hi [owner name], we received your land requirement for [broker name]". The worker processes the queue payload correctly (it has `eventName` + `variables`), so actual WhatsApp delivery is unaffected. But the audit trail is wrong for every broker image upload, document upload, and lead notification.

### Document filename length not capped

`properties.ts` image upload:
```ts
const safeName = part.filename.replace(/[^a-zA-Z0-9._-]/g, "_").slice(0, 120);
```

`workflows.ts` document upload:
```ts
const filename = `${Date.now()}-${part.filename.replace(/[^a-zA-Z0-9._-]/g, "_")}`;
```

The cap is missing in the document handler. The full path including timestamp prefix, property UUID, and sanitized name could exceed filesystem limits on some systems (ext4 limit is 255 bytes per component). The fix is one `.slice(0, 120)` after the replace.
